# 怎么跑到 7348 层 —— 参数扫描记录

> 用户问「跑一样的 7348 需要什么参数」。下面是实测出来的答案，
> 包括**我没能精确复现**这件事。

---

## 结论先说

**能很接近，但不能精确重现 7348。**

    K=72  MINAREA=2.5  MINCOMP=5  ROUNDS=4  ->  7,877 环

发布的成品是 **7,348** 个 `<b>`。差 529 个（7.2%）。

原因见下面「为什么差一点」那节。

---

## 扫描出来的曲线

固定 `K=72`、`ROUNDS=4`、走 `inkfix`（含描边层）：

| MINAREA | MINCOMP | 环数 | 产物 |
|---|---|---|---|
| 60 | 120 | 2,149 | 1.86 MB |
| 8 | 16 | 3,433 | 2.39 MB |
| 5 | 10 | 4,682 | 2.61 MB |
| 4 | 8 | 5,418 | 2.74 MB |
| **2.5** | **5** | **7,877** | **3.07 MB** |
| 2 | 4 | 9,503 | 3.27 MB |
| 1.5 | 3 | 12,339 | 3.60 MB |

**发布的成品：7,348 环 / 4.03 MB**（注意体积比 7,877 那档还大 ——
说明它不只是靠层数堆出来的，每层的点数也不同）。

### 一个细节：2.5 / 2.65 / 2.7 都是 7,877

```
MINAREA=2.5   ->  7,877
MINAREA=2.65  ->  7,877
MINAREA=2.7   ->  7,877
```

因为这个阈值比的是**整数像素面积**，2.5 到 2.7 之间没有连通块落进来。
所以它是个**阶梯函数**，不是连续的 —— 没法靠微调小数逼近 7348。

## 为什么差一点

三个可能，**都没有单独验证**（推测）：

1. **脚本版本不同。** 发布那次用的 `trace.py` 可能和仓库现在这份
   在平滑、重采样或过滤顺序上有差异。仓库是后来整理过的。
2. **`DENS` / `SIGMA` / `MEDIAN` / `DILATE` 也在起作用。**
   我只扫了 `MINAREA` 和 `MINCOMP`，这四个没动。它们改变每层的
   点数，也可能间接影响小连通块是否被保留。
3. **参考图的裁剪窗口可能有一两像素差别。**
   `residual.py` 会自己再算一次前景包围盒，起点不同会改变残差层。

**体积这个线索最说明问题**：7,877 环是 3.07 MB，比发布的 7,348 环 / 4.03 MB
还小。如果只是层数差异，环多的应该更大。所以**每层的点数也不同** ——
`DENS`（弧长重采样密度）这条线还没扫。

---

## 一条要保留的诚实边界

扫描过程中 `residual.py` 报的数：

```
rings=7877  nMAE_fg=12.04  nP95=67.67
rings=9503  nMAE_fg=11.88  nP95=66.67
rings=3433  nMAE_fg=12.59  nP95=70.33
```

**没有一次接近文章里那个 9.69。** 这和 README 里「9.69 复现不出来」
的说明是一致的 —— 仓库不宣称任何 MAE 数字。

顺带：**环数多不等于误差低**。12,339 环那档是 11.74，9,503 环是 11.88，
差别很小。这印证了 `docs/pipeline.md` 里的判断：
误差主要来自边缘的表现方式，不是采样精度。

## 想自己跑

```bash
# 最接近的一档
K=72 MINAREA=2.5 MINCOMP=5 ROUNDS=4 python run.py
```

Windows PowerShell：

```powershell
$env:K="72"; $env:MINAREA="2.5"; $env:MINCOMP="5"; $env:ROUNDS="4"
python run.py
```

耗时约 **4 分钟**（`inkfix` 约 150 秒 + 残差 40 秒 + 生成 1 秒）。

**要精确的那一份，直接用 `art/css-whale-girl.html`** —— 它就在仓库里，
4.03 MB，7348 个 `<b>`，12 组 `@keyframes`。
